# M1 Concept Questions ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
1. eval_expr returns Result<Value, Control>. Ok(v) means the expression means the expression returned a value. A stuck expression is when it cant further evaluate a step because it violates a runtime invariant the checker didnt catch. Stuck expressions come back as Err(Control) where the underlying error is a RuntimeError variant converted via .into(). For a type error, the RuntimeError::TypeError contains the type that was expected and the type that was actually found, along with the span of the operation that caused the error.

2. in Expr::Unary let v = self.ecal_xpr(sub, env)?; if evaluating sub gets stuck, it returns Err(Control::...), and ? immediately returns that Err from the outermost call, the unary arm never reaches its match (op, v). Without a ? it would look like:
    let v = match self.ecal_expr(sub, env) {
        Ok(v) => v,
        Err(e) => return Err(e),
    };

3. In my and / or implementation it evaluates lhs first and uses a match to decide wheather the rhs needs to be evauluated. For and, the right side is only evaluated whent he left side is true. For or the right side is only evaluated when the left side is false. The rhs self.eval.expr call is inside the appropriate match branch, so it is skipped when the left side already determines th result.

4. Add, Sub, Mul, Div, and Mod use wrapping_add, wrapping_sub, and so on. Using wrapping methods makes the overflow a defined behavior instead of a lanugage panic that would crash the interpreter. The wrapping behavior is explicityly requested by using theses wrapping methods,so it doesnt depend on compiler settings.

5. every stuck expression uses span: *span, where span belongs to the enclosing Expr node being evaluated. the Expr::Binary arm uses its own span when a type error occurs. This is useful because the span points to the operation that caused the runtime error instead of pointing to a larger enclosing expression or only to a sub expression

# How I implemented it

1. In my Expr::Binary arm and / or are peeled off first and handled with short-circuiting match / return, since after this evaluation is safe. For all other operators both operators are evaluated: let l = self.eval_expr(lhs, env)?; let r = self.eval_expr(rhs, env)?; using ? twice here so that a stuck lhs shor circuits before the rhs is even looked at. Eq/Ne just compare the values with == and !=. The int only group does one match (&l, &r) to pull out ints or bail with a type error for whichever side want an int, then a second match op dispatches to the wrapping arithmetic with Div/Mod checking if b == 0 first before returning. Concat matches (l, r) structurally, Str + str builds a new Rc<str>, List + List calls .concat() and anything else is a type error. Cons checks that the right operand is a list and if it is it calls List::cons(l, tail) to put the left value at the front, otherwise a type error will be reported. Also every error path ends in into() to lift a runtime error into whatever COntrol wraps it, the ? or return gets it out of eval_expr.

# M4 Concept Questions ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
1. When |x| x + y is evaluated my lambda arm stores the parameter names, a clone of the body, and a clone of the current environment in a closure. At that moment y is bound to 1. In my call arm let mut call_env = captured.clone(); starts from the closures environment and looking up y finds 1. If I had extended the callers environment the nearest y would be the let y = 100 binding and the result would be 101. The name of this scoping disipline the interpreter uses is lexical/static scoping.

2. My call arm evaluates operator first and checks NotAFunction, and then evaluates the arguments left to right. Then it checks the arity, and lastly runs the body. In 5(print(1)) the operater 5 isnt a closure so the arm returns NotAFunction before the argument is evaluated, so print(1) never runs. In (|x, y| 0)(print(1)) prints 1 then gets stuck because the operator is a closure and the arguments are evaluated. Then the arity check fails with ArityMismatch before the body can run. Both errors carry the span of the whole call expression.

3. I take the bodys result without ? in let result = self.eval_expr(body, &call_env);. I call self.leave_call() then match result { Err(Control::Return(v)) => Ok(v), other => other }. A return becomes the calls value, and Ok and Raise pass through unchanged. If I used ? on the body, an Err would return before the leave_call ran, so the frame count wouldnt be decremented. A return would also escape the call instead of being caught so the caller would get the return as an error instead of v.

4. In sum_to(1000000) the amount of calls in progress at the deepest point would be 1 million since each call happens inside of the previous one, but enter_call stopps it at the frame limit. My enter_call adds one to the depth and leave call subtracts one, and enter_call returns a stack overflow at the limit. In fold, there is only one frame in progress at any moment, because the callback finishes before the next one starts and the depth stays small. A native like fold evaluates an ordinary call expression with self.eval_expr and that goes through my call arm, so it gets the same arity check and return handling.

5. The environment my lambda captures is at the point where the lambda is evaluated. The let only extends the environment after the RHS has been evaluated, so fact doesnt exist yet and the recursive call is an UnboundVariable. The driver gives every top level function the root environment and stores all of them in that root so fact is visible inside its own body.

# How I implemented it
1. I destructure Expr::Call(callee, args, span). I evaluate the operator with self.eval_expr and return NotAFunction, using type of for found, if it isnt a Value::Closure. I then evaluate each argument left to right into vals using ?. I match on &*closure. For Closure::Native(id) I call self.eval_prelude(*id, vals, *span) and convert its RuntimeError into a control with .map_err(Control::from). For CLosure::Bridger I check params.len() against vals.len() and return ArityuMismatch. Then I extend a clone of the captured environment with each parameter and value using env.extend. I call enter_call, evaluate the body, call leave_call and finally turn a return into the calls value. My lambda arm evaluates nothing, it builds a Closure::Bridger from the parameter names, a clone of the body, and the current environment, and drops type annotations.
